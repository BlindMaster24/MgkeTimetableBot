## Overview

MGKCT Timetable Bot is a Telegram bot that shows the timetable of the Minsk State College of Digital Technologies.

It is a complete port of the old TypeScript bot to Go: the same commands, menus, buttons and wording, without VK / Viber / Alice — Telegram and the HTTP API only. The surface (commands, callback prefixes, button labels) is guarded by an automated TypeScript parity check, see [Parity with the TypeScript bot](#parity-with-the-typescript-bot).

Features:

- day and week timetable for a group or a teacher, including the odd/even week split;
- bell schedule that refreshes itself from the college site;
- timetable rendered as a PNG image (pure Go, no CGO);
- ICS export and two-way Google Calendar integration;
- timetable archive in SQLite plus change notifications;
- configurable menus: output format, view options, notifications, comparison, aliases;
- REST API built on gin.

## Stack

- [telego](https://github.com/mymmrac/telego) — Telegram Bot API (long polling)
- [gin](https://github.com/gin-gonic/gin) — HTTP server and REST API
- [goquery](https://github.com/PuerkitoBio/goquery) — HTML parsing
- [zerolog](https://github.com/rs/zerolog) + [lumberjack](https://github.com/natefinch/lumberjack) — logging and rotation
- [go-i18n](https://github.com/nicksnyder/go-i18n) — localization (`internal/i18n/locales/ru.json`)
- [modernc.org/sqlite](https://pkg.go.dev/modernc.org/sqlite) — pure-Go SQLite, no CGO
- [fogleman/gg](https://github.com/fogleman/gg) — timetable PNG rendering
- [robfig/cron](https://github.com/robfig/cron) — notification scheduler
- [yaml.v3](https://pkg.go.dev/gopkg.in/yaml.v3) — configuration
- ICS is generated by hand in `internal/calendar`, no external library

## Requirements

- **Go 1.27.1 or newer** — the minimum is pinned in `go.mod` (`go 1.27.1`), an older toolchain refuses to build the module. With `GOTOOLCHAIN=auto` (the default) Go downloads the required version automatically.
- No CGO: SQLite and image rendering are pure Go.
- A writable directory for `cache/` and the database files.

Check your version:

```bash
go version   # expect go1.27.1 or newer
```

## Install and run

1. Clone the repository:

    ```bash
    git clone https://github.com/BlindMaster24/MgkeTimetableBot.git
    cd MgkeTimetableBot
    ```

2. Create the config from the template and fill it in:

    ```bash
    cp configs/config.example.yaml configs/config.yaml
    # set telegram.token, telegram.admin_ids, http.port, Google keys, etc.
    ```

3. Download dependencies:

    ```bash
    go mod download
    ```

4. Run the bot:

    ```bash
    go run ./cmd/bot/ -config configs/config.yaml
    ```

5. Or build a binary and run it:

    ```bash
    go build -o bot ./cmd/bot/
    ./bot -config configs/config.yaml
    ```

The config path can also come from the `CONFIG_PATH` environment variable — the `-config` flag wins. Without either one `configs/config.yaml` is used.

A single process hosts Telegram long polling, the HTTP server (API plus the Google OAuth callback) and the parser goroutine.

## Configuration

Everything lives in `configs/config.yaml` (template: `configs/config.example.yaml`).

| Section | Purpose |
|---------|---------|
| `dev` | Development mode (verbose logs, dev commands) |
| `db_path` | SQLite file with the timetable archive (default `./sqlite3.db`) |
| `chat_db_path` | SQLite file with chats, aliases, subscriptions and Google accounts (default `./bot_chats.db`) |
| `cache_dir` | Directory of the file-backed timetable cache (default `./cache/rasp`) |
| `logging` | Level, log file, rotation settings |
| `http` | Server name and HTTP port (API and Google OAuth) |
| `telegram` | Bot token, admin IDs, the `noticer` flag |
| `api` | Base path of the REST API |
| `google` | OAuth client, service account, `calendar_owners` |
| `calendar.ics.enabled` | Enable the ICS export and its menu button |
| `accept` | What to show in the timetable (rooms, private entries) |
| `parser` | Poll intervals, sources, bell schedule, proxy |
| `timetable` | Fallback bell schedule: `weekdays`, `saturday`, `shortened_1h` (used when the site is unreachable) |
| `health` | Alert thresholds: parser, calendar sync, API errors |
| `encrypt_key` | Encryption key (for `createApiKey` / `decryptKey`) |
| `global_noticer` / `global_adblock` | Global notification and advertising switches |

The timetable cache is stored as JSON in `cache/rasp/`, the archive lives in SQLite (see `db_path` and `migrations/001_init.up.sql`).

### Environment variables

Every config field can be overridden by an environment variable — handy for Docker and CI, where secrets do not belong in a file.

- the default name is the `MGKE_` prefix plus the field path joined with `_`: `MGKE_HTTP_PORT`, `MGKE_DB_PATH`, `MGKE_PARSER_ENABLED`, `MGKE_TELEGRAM_TOKEN`, `MGKE_GOOGLE_SERVICE_ACCOUNT_PRIVATE_KEY`;
- a few fields keep short historical aliases: `DEV`, `DB_PATH`, `LOG_LEVEL`, `HTTP_SERVER_NAME`, `HTTP_PORT`, `TG_TOKEN`, `ENCRYPT_KEY`. When both names are set, `MGKE_*` wins;
- precedence: the `-config` flag, then environment variables, then the config file. The only exception is `CONFIG_PATH`, which merely selects the file when the flag is absent;
- `MGKE_*` overrides any YAML value, and an empty string counts as an explicit value (`MGKE_ENCRYPT_KEY=`);
- lists are comma-separated: `MGKE_TELEGRAM_ADMIN_IDS=1,2,3`;
- booleans accept `true/false`, `1/0`, `yes/no`, `on/off`;
- complex structures (for example the bell schedule tables in `timetable.weekdays`) stay in YAML; setting such a variable fails loudly instead of being ignored;
- an invalid value (for example `MGKE_HTTP_PORT=abc`) also fails at startup and names the variable.

```bash
CONFIG_PATH=configs/config.yaml \
MGKE_TELEGRAM_TOKEN=123:ABC \
MGKE_HTTP_PORT=8080 \
MGKE_PARSER_ENABLED=true \
MGKE_TELEGRAM_ADMIN_IDS=1,2,3 \
./bot
```

`config.EnvNames()` returns every supported variable name.

### Parser

- `parser.enabled` — enable the background parser;
- `parser.endpoints.*` — site URLs: group timetable, teacher timetable, teacher list, bell schedule;
- `parser.update_interval.*` — poll intervals: regular, during activity hours, after an error, for the teacher list, for the bell schedule;
- `parser.alertable_ignore_filter` and `parser.lesson_index_if_empty` — which lessons count as meaningful in change notifications;
- `parser.calls.enabled`, `parser.calls.prefer_site`, `parser.calls.notify` — bell schedule: enabled, site versus manual edits, notify on changes;
- `parser.proxy` — HTTP(S) proxy for site requests.

The bell schedule refreshes itself from the college site; it can still be edited by hand from the calls menu.

The `parser.v2.*` keys come from the old TypeScript bot and are not read by the Go version — they are no longer part of the example config.

## HTTP API

The server listens on `http.server_name:http.port`:

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/info` | Service information and version |
| GET | `/api/groups` | Group list |
| GET | `/api/teachers` | Teacher list |
| GET | `/api/group/:name` | Group timetable |
| GET | `/api/teacher/:name` | Teacher timetable |
| GET | `/api/parser-health` | Cache counters: hits, misses, last update time |
| GET | `/api/health` | Health metrics (parser, calendars, API) and active alerts; 503 while alerting |

`google.url` (default `/google/oauth`) is the Google OAuth callback the user returns to after authorization.

## Metrics and health

Counters are kept in memory (`internal/health`) and served by `GET /api/health`. The endpoint returns metrics plus active alerts, and answers with `503` whenever an alert is active, so it can be wired straight into monitoring.

| Group | Metrics | Alerts |
|-------|---------|--------|
| Parser | runs and errors, consecutive failures, time since the last successful parse, cycle duration | failure streak, stale data |
| Google Calendar | runs and errors, consecutive failures, days synced | failure streak, no successful sync for too long |
| HTTP API | requests, 5xx responses, recent errors, slowest request | burst of 5xx responses |

Alerts go to the administrators (`telegram.admin_ids`) as a Telegram message with the details. They repeat at most once per `cooldown_minutes` while the problem persists, and a recovery message follows once it is gone. Thresholds are configured in the `health` section:

```yaml
health:
  disabled: false              # turn alerts off completely
  check_minutes: 1             # how often to evaluate
  cooldown_minutes: 30         # pause between reminders
  parser_stale_minutes: 15     # the timetable has not been refreshed for so long
  parser_failures: 3           # consecutive failed parses
  calendar_stale_minutes: 360
  calendar_failures: 3
  api_errors: 20               # 5xx responses inside the window
  api_window_minutes: 5
```

Every field is also available as an environment variable (`MGKE_HEALTH_PARSER_STALE_MINUTES` and so on).

## Notifications

The scheduler (`internal/notification`) starts with the bot and sends:

- timetable changes for today and tomorrow;
- the timetable for a new week;
- bell schedule changes;
- parser errors.

Events are produced by the parser, queued in the cache and drained after every parse cycle. Every notification type can be turned off from the notification menu (`/notice`), and each chat keeps its own settings.

## Google Calendar and ICS

- `docs/google-calendar.md` — Google Cloud setup, OAuth, account linking, permissions.
- Google menu: `/google_calendar` or the “📅 Google Calendar” button in the main menu — list calendars, add one, grant or revoke write access.
- Synchronization is event-driven: after every parse cycle the parser reports only the days that actually changed, and the bot refreshes exactly those days instead of re-reading the whole archive. A day is cleared of its old events before new ones are written, and lesson times come from the bell schedule.
- A separate reconcile pass catches up calendars that fell behind (the bot was offline, a new week started). It only fetches the missing days and never rewrites days that are already synchronized.
- ICS: `/ics` when `calendar.ics.enabled` is on.

## Docker deployment

```bash
docker compose up -d --build
```

`docker-compose.yml` builds the image from the `Dockerfile`, ships the config `configs/config.yaml` and keeps state (`bot_chats.db`, `sqlite3.db`, `cache/`, logs) in a named volume. Secrets are passed as environment variables:

```yaml
services:
  bot:
    environment:
      MGKE_TELEGRAM_TOKEN: "123:ABC"
      MGKE_TELEGRAM_ADMIN_IDS: "1,2"
      MGKE_DB_PATH: /data/sqlite3.db
```

What to know about the image:

- multi-stage build: the binary is compiled on `golang:1.27.1` and the runtime image only carries the binary, the config template and the certificates;
- the process runs as an unprivileged user, CGO is not needed (SQLite and image rendering are pure Go);
- a built-in `HEALTHCHECK` calls `GET /api/health` every 30 seconds and marks the container unhealthy while alerts are active;
- only the HTTP port (`http.port`) is published — Telegram works over long polling, so no inbound ports are required;
- state lives in the `/data` volume, and the config can be replaced through `CONFIG_PATH`.

## Development

```bash
go build ./...                                          # build
go vet ./...                                            # static analysis
go test -count=1 -p 1 ./internal/... ./tests/...         # all tests
go test -count=1 -p 1 ./internal/... ./tests/... -cover  # with coverage
```

Focused runs:

```bash

```

`-p 1` is not required semantically but it noticeably lowers peak memory usage on small machines and in CI.

### Parity with the TypeScript bot

The old TypeScript bot lives on the `go` branch of this repository. `scripts/paritycheck` reads it straight from git and compares three surfaces: Telegram command names, callback data roots and every keyboard button label.

```bash
go run ./scripts/paritycheck                 # compare against the go branch
go run ./scripts/paritycheck -ts-ref origin/go
go run ./scripts/paritycheck -update         # regenerate the TypeScript fixture
go run ./scripts/paritycheck -dump-go        # print the live Go surface
```

- `internal/telegram/testdata/parity/ts_surface.json` — the recorded TypeScript surface;
- `internal/telegram/testdata/parity/known_differences.json` — accepted differences, **every entry must carry a `reason`**, otherwise the check fails;
- `internal/telegram/parity_test.go` re-checks the same surface offline, so a plain `go test` catches drift without the TypeScript branch.

Keyboard layouts are stored in the golden file `internal/telegram/testdata/keyboard_layouts.golden`: the test renders every builder across the mode and view-flag matrix and fails on any shifted button.

```bash
go test ./internal/telegram -run Golden          # verify layouts
go test ./internal/telegram -update              # rewrite the golden file
```

CI (`.github/workflows/go-ci.yml`) runs the same checks: the `build` job builds, vets and tests, the `parity` job compares against the `go` branch and verifies the golden layouts.

The `tests/docs_test.go` suite keeps this documentation honest: it asserts that every bot command, every API route and the minimum Go version from `go.mod` appear in both README files, and that every top-level config key is documented.
